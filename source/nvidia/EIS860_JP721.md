# E8I6S0_JP721

基于 JP 7.2.1（L4T R39.2.1）的 EIS860 载板适配整理。参考 JP621（JetPack 6.2.1 / L4T r36.4.4）的适配流程，将 EIS860 载板的全部定制（pinmux / GPIO / USB / PCIe / RGMII / EEPROM 跳过 / ODMDATA）移植到 JP 7.2.1。

## 版本信息

| 项目 | JP621 (旧) | JP721 (本目录) |
|------|-----------|---------------|
| Jetpack | 6.2.1 | 7.2.1 |
| L4T | r36.4.4 | R39.2.1 |
| 内核 | 5.15.148-tegra | 6.8.12-tegra |
| Ubuntu | 22.04 (jammy) | 24.04 (noble) |
| 内核源码目录 | kernel-jammy-src | kernel-noble |
| 工具链 | aarch64-buildroot-linux-gnu- (gcc 2022.08) | aarch64-none-linux-gnu- (gcc 13.2.0) |
| EIS860_VERSION | 5.4 | 7.2 |

### 6.1 PHY MODE 寄存器修复（eth0 无法 link）

#### 硬件背景

```
RJ45 网口 ←→ Marvell 88E1512 PHY 芯片 ←→ (RGMII 接口) ←→ Orin 芯片内部 EQOS 网口 MAC
```

88E1512 内部有一个**模式寄存器（Page 18, Reg 20）**，其 `MODE[2:0]` 位决定 PHY 的工作模式：

| MODE 值 | 含义 |
|---------|------|
| 0 | RGMII 转铜口（EIS860 需要的模式） |
| 1 | SGMII 转铜口 |
| 2/3 | RGMII 转 1000X / 100FX 光口 |
| 7 | **未定义的非法模式** |

#### 故障现象

烧录后 eth0 一直 link 不上，通过 MDIO 直接读 PHY 寄存器排查，发现：

- MDIO 通信正常（能读到 PHY ID `0x01410dd4`，读写寄存器都正常）
- PHY 能响应配置（写 BMCR 寄存器能生效）
- **但铜口收发器完全不工作**：
  - `BMSR` 寄存器：link = 0（链路始终为 down）
  - `ANLPAR` 寄存器 = 0x0000（**完全检测不到对端设备**——网线插着却像没插一样）
  - 自协商永远无法完成

#### 排查过程

按顺序排除了各个可疑点：

| 排查项 | 结果 |
|--------|------|
| EQOS 引脚 pinmux 配置 | ✅ 正常（引脚都已复用为 eqos 功能） |
| PHY 复位 GPIO（G5）时序 | ✅ 正常 |
| MDIO 总线通信 | ✅ 正常 |
| PHY 供电/掉电状态（BMCR bit11） | ✅ 正常 |

pinmux 对、MDIO 通、PHY 能配置，但就是 link 不上——说明问题出在 **PHY 芯片内部模式配置** 上。

接着用 MDIO 工具直接读 `Page 18, Reg 20`（MODE 寄存器），发现：

```
MODE 寄存器 = 0x0007  →  MODE[2:0] = 7
```

`MODE=7` 是未定义模式。PHY 处于这个非法模式下，铜口收发器不会被正确使能，所以永远检测不到网线对端。

#### 根因

这个寄存器的值来自两个途径：

1. **硬件上电复位时**，由芯片 strapping 引脚决定初始值 → 这块板子的 strapping 产生的就是非法值 7
2. **软件通过 MDIO 写入**纠正它

关键在于第 2 点：**内核里的 Marvell PHY 驱动（marvell.c）在 RGMII 模式下根本不会去初始化这个 MODE 寄存器。** 看驱动代码 `m88e1510_config_init`（kernel-noble/drivers/net/phy/marvell.c:1210）：

```c
/* SGMII-to-Copper mode initialization */
if (phydev->interface == PHY_INTERFACE_MODE_SGMII) {
        err = marvell_set_page(phydev, 18);      /* 选 page 18 */
        ...
        /* 只有 SGMII 接口时才会写 MODE 寄存器 */
        err = phy_modify(phydev, MII_88E1510_GEN_CTRL_REG_1,
                         MII_88E1510_GEN_CTRL_REG_1_MODE_MASK,
                         MII_88E1510_GEN_CTRL_REG_1_MODE_SGMII);
        ...
}
```

只有接口类型是 **SGMII** 时驱动才写 MODE 寄存器；我们是 **RGMII**，驱动直接跳过。于是 PHY 就带着硬件 strapping 给的非法值 7 运行，铜口自然 link 不上。

#### 修复方案

内核驱动提供了一个 DT 属性 `marvell,reg-init`，格式是一组 `<page reg mask value>` 条目，由 `marvell_of_reg_init()`（marvell.c:499）在 `config_init` 阶段逐条执行：

```c
val = read(reg);
val &= mask;      /* mask 中为 1 的位保留，为 0 的位清零 */
val |= value;     /* 再或上 value */
write(reg, val);
```

原本的 DT 只有一条 LED 中断配置。修复就是在 `marvell,reg-init` 里**追加第二条条目**，让驱动在初始化时把 MODE 寄存器纠正过来：

```
marvell,reg-init = <0x03 0x12 0x7fff 0x880>, <0x12 0x14 0xfff8 0x0030>;
                   └── 原有: LED[2] 中断配置 ──┘   └── 新增: MODE 寄存器修复 ──┘
```

新增条目 `<0x12 0x14 0xfff8 0x0030>` 的含义：

| 参数 | 值 | 含义 |
|------|-----|------|
| page | `0x12`（18） | 切到 MODE 寄存器所在的页 |
| reg | `0x14`（20） | 目标是 General Control Register 1 |
| mask | `0xfff8` | 读出当前值后：保留 bit15:3，**清零 bit2:0（MODE 位）** |
| value | `0x0030` | 再或上 `0x0030`：**置位 bit5/bit4** |

执行后寄存器值变为 `0x0030`：

```
0x0030 = 0000 0000 0011 0000
                 ↑↑
                 bit5=1, bit4=1  → RGMII TX/RX 延迟使能（对应 DT 里 phy-mode = "rgmii-id"）
         bit2:0 = 000            → MODE = 0（RGMII 转铜口）✓
```

这样每次启动时驱动都会自动把 PHY 从非法模式 7 纠正为正确的 RGMII-to-copper 模式。

#### 修复验证

调试时先在运行中的设备上通过 MDIO 手动做了同样的事来验证：

1. 通过 MDIO 写 `0x0030` 到 Page 18, Reg 20（设 MODE=0 + 延迟位）
2. 触发 PHY 复位让新模式生效
3. 重启 eth0 接口 → **链路成功协商，DHCP 拿到 IP，ping 通** ✅

确认有效后，才把这个修复固化到 BSP 源码和 patch 里（`tegra234-base-overlay.dtsi` 第 273 行，`jp7-rgmii.patch` 第 49 行），并通过了 patch 往返验证和 cfg.sh 完整补丁链验证。

### 7.2 USB 冷启动识别异常

更新日期：2026-11-02。适用对象：EIS860 底板、Jetson Orin 模组、当前 JP721 适配工程。原始记录见 [JP721_USB冷启动识别异常_调试与修复.md](/home/ieit/jetson_flash/JP721/JP721_USB冷启动识别异常_调试与修复.md)。

#### 现象与结论

U 盘保持插入 USB3 接口，冷启动后没有枚举；拔插 U 盘后可以正常识别。故障时 USB3 Hub 已枚举，但同一个物理 Hub 的 USB2 上行 `1-1` 缺失，即使 USB0 的 role 文件显示 `host`，也没有建立预期的 USB2 主机连接。

本次验证了有效恢复动作：在正常系统中将 USB0 从 `host` 切到 `none`，等待 2 秒，再切回 `host`。不拔插 U 盘、不修改 companion 和休眠参数，即可先恢复 `1-1`，随后 U 盘以 5Gb/s 枚举。

最终采用启动脚本恢复：先设置 host 并等待 Hub0；只有 Hub0 未出现时才执行一次角色切换。修改后启动日志确认该分支自动执行并成功识别 U 盘。

**原因判断的边界：**已将排查重点收敛到 USB0 首次角色切换后的主机连接建立过程。尚未通过驱动跟踪确定是通知处理、PHY/端口状态、初始化时序还是板级切换控制交互导致；不能把“重新切换有效”直接等同于某一项内核缺陷已经证实。当前方案是经过现场验证的恢复措施，不是底层驱动修复。

- 14.136秒：`2-2.1` 以 SuperSpeed 枚举。
- 15.222秒：`sda` 挂接完成，`sda1` 存在。

更早一次 JP621 日志显示，`eis860init` 执行后紧接着出现 `1-1` 和 U 盘。该时序与角色切换促成枚举相符，但单纯时间相关不能替代驱动调用跟踪。

##### JP721 在线恢复

故障现场：role=host、companion=1、autosuspend=2，没有 `1-1` 和 U 盘。确认 USB0 无已枚举下游设备后执行一次角色切换，未改变物理接线：

- 562.014秒：`1-1` 开始枚举。
- 562.250秒：U盘 `2-2.1` 枚举。
- 563.351秒：`sda/sda1` 生成。

恢复后读取 U 盘64MiB成功，约117MB/s；使用直接只读方式，没有向 U 盘写入数据。该结果仅证明本次短读成功，不代表完整介质或持续性能测试。

##### companion=0 试验与回退

按原理图 USB2 接线，曾将 **BSP/build 中 usb3-1 companion 从1改为0**，由用户编译烧录测试。实际DTB确认修改生效，但 initrd 烧录在 RCM 下载后等待 USB 网络阶段超时。

串口确认内核和烧录 initrd 已启动，role=device，gadget已绑定 `3550000.usb`，usb0已有IPv6地址，但UDC停在 `default`，未进入 `configured`。拔插刷机线仍未恢复。

因此该试验没有提供运行系统中U盘故障已修复的证据，也不能单凭超时断言精确的刷机失败根因。build源码已恢复为1。本次最终方案保持原 companion 配置，没有将0加入正式补丁。原理图映射与软件角色行为的关系仍是后续研究项。

#### 修复方案：启动脚本条件恢复

源文件：[rootfs_files/shell/eis860init.sh](EIS860_JP721_files/eis860init.sh)  
设备文件：`/usr/local/bin/eis860init.sh`  
服务：`eis860init.service`，现有正常系统启动服务。

恢复流程：

1. 等待 `/sys/class/usb_role/usb2-0-role-switch/role` 可写，最多10秒。
2. 写入 `host`，等待Hub0最多5秒。
3. 检查 `1-1` 的VID:PID是否为 `0451:8027`。已经出现时直接继续启动，不切换角色。
4. 若 `1-1` 已存在但不是预期Hub，记录错误并跳过恢复，避免断开其他设备。
5. 若该路径仍缺失，执行一次 `none`，等待2秒，再写入 `host`，等待Hub最多8秒。
6. 记录成功或失败，不循环恢复。USB检查失败仍继续原有防火墙和MCU启动任务。

判断对象是常驻的Hub0，而不是U盘。没有插U盘也应正常完成检查。脚本提供EXIT trap，在none阶段发生可处理的退出时尝试恢复host；它不能覆盖断电或SIGKILL等情况。

每次脚本调用最多尝试一次恢复；不是跨进程的“每次开机只能调用一次”锁。不要为了查看USB状态反复运行整个脚本，因为其他启动任务也会被重复执行。

本方案仅加入正常rootfs启动流程，未修改initrd刷机脚本、companion或autosuspend参数。角色切换可能短暂影响共享USB0的刷机口；适用场景是本板正常开机后需要Hub0的主机模式。

## 8 与 JP621 补丁的差异

1. **jp7-uas.patch 已移除**：Jetpack 7 上游已合并 UAS 补丁（`xhci-tegra.c` 已含 `can_do_streams`）
2. **jp7-usb-pcie.patch 目标文件变更**：
   - JP621: `tegra234-p3737-0000+p3701-0000.dts`（含完整 USB/PCIe 配置）
   - JP7: `tegra234-p3737-0000+p3701.dtsi`（配置移至此文件）
3. **jp7-rgmii.patch EQOS 地址变更**：
   - JP621: `ethernet@6810000`
   - JP7: `ethernet@2310000`（JP7 DT 重构）
4. **UEFI 结构变更**：
   - JP621: `bootloader/uefi_jetson.bin`
   - JP7: `bootloader/uefi_bins/uefi_t23x_general.bin`

## 9 补丁应用方式

使用脚本 `patch/cfg.sh`：

```shell
#!/bin/bash
echo 'Execute this script in the top-level directory.'
TOP_DIR=$(pwd)
BSP_DIR=$TOP_DIR/BSP
L4T_DIR=$BSP_DIR/Linux_for_Tegra
SRC_DIR=$L4T_DIR/source

# UEFI: JP7 结构变更, UEFI 位于 bootloader/uefi_bins/uefi_t23x_general.bin
# 如有定制 UEFI, 请将文件放至 patch/uefi_t23x_general.bin 并取消下行注释
# cp "$TOP_DIR"/patch/uefi_t23x_general.bin "$L4T_DIR"/bootloader/uefi_bins/uefi_t23x_general.bin

# L4TConfiguration.dtbo (如需定制 overlay, 取消下行注释)
# cp "$TOP_DIR"/patch/L4TConfiguration.dtbo "$L4T_DIR"/kernel/dtb/L4TConfiguration.dtbo

# 1. bootloader patch (pinmux BCT / GPIO / mb2-bct / ODMDATA) - 在 Linux_for_Tegra 下应用
cd "$L4T_DIR" || exit 1
patch -p1 < "$TOP_DIR"/patch/jp7-bootloader.patch

# 2. 内核源码补丁 (USB/PCIe / RGMII) - 在 source 下应用
cd "$SRC_DIR" || exit 1
patch -p1 < "$TOP_DIR"/patch/jp7-usb-pcie.patch
patch -p1 < "$TOP_DIR"/patch/jp7-rgmii.patch

# 注: jp6-uas.patch 已被 Jetpack 7 上游合并 (xhci-tegra.c 已含 can_do_streams), 无需再打

cd "$TOP_DIR" || exit
echo "[OK] All patches applied."
```
